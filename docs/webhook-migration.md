# Retiring the WooCommerce webhook path

**Status:** planned, not started. The backend side is annotated as deprecated
(`backend/app/routers/webhooks.py`, `license_service.get_client_license`); no
PHP has been touched.

**Who this is for:** whoever implements the `semantic-search-woo` change. It is
written so you do not have to read both plugins first.

---

## 1. Why this has to happen

`llm_key_service.decrypt_key` (`backend/app/services/llm_key_service.py:21`)
derives its AES key as `sha256(license_key)`. The merchant's licence key is
therefore the key-encryption key for every provider key they have stored — the
LLM key and, since the per-tenant embedding work, the embedding key too. Both
plugins and all three Magento modules wrap under the same scheme.

Every other caller of `resolve_embedding_key` takes that plaintext key **from
the request**: `routers/sync.py` and `routers/ingest.py` read it out of the
body, the WordPress namespace reads it off the `Authorization` header. The
WooCommerce webhook path cannot, because the caller is WooCommerce itself and
WooCommerce presents no licence key. So it does the only thing left and reads
the key back out of the database:

```
webhooks.process_upsert()
  -> license_service.get_client_license(db, client_id)     # SELECT lk.license_key
  -> resolve_embedding_key(embedding_blob, llm_blob, license_data["license_key"])
  -> decrypt_key(blob, license_key)                        # sha256(license_key)
```

`schema_v2` stores `licences.key_hash` — a SHA-256 hex digest — and has no
plaintext column anywhere. A hash cannot be un-hashed. There is no rewrite of
`get_client_license` that works against v2, and no rework of `webhooks.py` that
recovers a KEK from a request that never carried a credential. The path does
not get ported; it gets deleted, and the work it was doing moves into the
plugin.

This is not a new pattern. `ai-product-qa-woo` already works the other way
round, and `semantic-search-woo` already does half of it.

## 2. What exists today

### 2.1 The three endpoints and what fires them

All three live in `backend/app/routers/webhooks.py`, mounted under `/api` by
`backend/app/main.py:48`.

| Endpoint | WooCommerce topic | What it does |
| --- | --- | --- |
| `POST /api/webhook/product-created` | `product.created` | embed + upsert |
| `POST /api/webhook/product-updated` | `product.updated` | embed + upsert, or remove when the product left `publish` |
| `POST /api/webhook/product-deleted` | `product.deleted` | remove the point |

None of them is called by our PHP. `SSW_Webhook_Manager::register()`
(`semantic-search-woo/includes/class-webhook-manager.php:34`) creates them
through the **store's own** WooCommerce REST API, using the merchant's
WooCommerce consumer key and secret, and bakes the tenant identity and both
encrypted provider keys into the delivery URL as query parameters
(`class-webhook-manager.php:79-85`) because a WooCommerce webhook has no other
way to carry them. WooCommerce then POSTs the product object directly to us.

Authentication is `?client_id=` plus an HMAC-SHA256 body signature under a
shared secret (`webhooks.py:verify_signature`). The secret is generated by the
plugin (`class-webhook-manager.php:311`) and pushed to
`POST /api/register-webhook-secret` (`backend/app/routers/webhook_secret.py`),
which stores it on `clients.webhook_secret`. So the caller proves it knows the
webhook secret; it never proves it holds a licence.

Two consequences worth naming, because both change after the cutover:

* **The webhook path does not run `DomainAuthorizer`.** Every other write
  endpoint does. See trap 6.2.
* **Registered webhooks are a snapshot.** The provider keys are frozen into the
  delivery URL at registration time, which is why the plugin re-registers when
  the licence key changes (`admin/assets/js/admin.js:598-608`) and why the
  settings screen carries a "Re-register Webhooks" button at all.

### 2.2 Exactly where the plaintext key is used

| Site | Field used | Why |
| --- | --- | --- |
| `webhooks.py` `process_upsert` | `license_data["license_key"]` | **the KEK.** Passed to `resolve_embedding_key`. This is the blocker. |
| `webhooks.py` `process_upsert` | `license_data["domain"]` | names the Qdrant collection; also `product_exists`, `get_client_product_count`, `_has_full_woo_payload` |
| `webhooks.py` `process_upsert` | `license_data["product_limit"]` | catalogue ceiling for new products |
| `webhooks.py` `product_deleted` | `license_data["domain"]` | names the Qdrant collection, nothing else |

Only the first is unfixable in place. The other three are ordinary lookups that
`licensing_service.resolve_key(db, presented_key)` answers better — it returns
`collection_name` and `catalogue_limit` from their own levels, with a separate
log line per denial reason instead of `get_client_license`'s single "no row".

### 2.3 What semantic-search-woo already does the right way

`SSW_Sync::register_hooks()` (`includes/class-sync.php:98`) already hooks
`woocommerce_update_product`, `woocommerce_new_product` and both variation
hooks, defers to a `ssw_sync_single_product` scheduled event, and pushes the
full formatter payload to `POST /api/sync/batch` via `send_batch()`
(`class-sync.php:514`). That is the push method. It exists because the backend
declines to let a webhook overwrite a point holding the full payload
(`webhooks._has_full_woo_payload`), which had already made the webhook upsert
path a no-op for stores this plugin indexes.

So the create and update halves are, in practice, **already migrated**. What is
missing is delete, unpublish, and the auth shape.

## 3. The replacement pattern, from ai-product-qa-woo

Two files carry the whole pattern.

### 3.1 `ai-product-qa-woo/includes/class-sync.php` — hooks

`AIPQA_Sync::register_hooks()` (line 71) registers, among others:

```php
add_action('woocommerce_update_product', [self::class, 'queue_product_sync'],   10, 1);
add_action('woocommerce_new_product',    [self::class, 'queue_product_sync'],   10, 1);
add_action('woocommerce_delete_product', [self::class, 'queue_product_delete'], 10, 1);
add_action('woocommerce_trash_product',  [self::class, 'queue_product_delete'], 10, 1);
add_action('aipqa_sync_single_product',   [self::class, 'run_single_sync'],   10, 1);
add_action('aipqa_delete_single_product', [self::class, 'run_single_delete'], 10, 1);
```

WooCommerce's own product hooks, not `save_post`: `save_post` also fires for
autosaves, revisions and quick-edits of unrelated fields, and hands over a
`WP_Post` rather than a product. Every queue method defers through
`wp_schedule_single_event()` (line 118-130), which de-duplicates identical
`(hook, args)` pairs inside a ten-minute window — WooCommerce fires
`woocommerce_update_product` several times for one editor click, and all of
them should collapse to one embed. It also keeps the merchant's "Update" button
from blocking on an embed, and keeps a save from failing outright when the API
is down.

Unpublish is handled inside the sync, not by a separate hook
(`class-sync.php:506`):

```php
if (get_post_status($product_id) !== 'publish') {
    return $this->delete_single($product_id);
}
```

Status is checked **before** formatting, deliberately: a trashed product whose
formatter returns `null` would otherwise never be removed.

### 3.2 `ai-product-qa-woo/includes/class-api-client.php` — transport

`AIPQA_API_Client::build_headers()` (line 391) is the whole contract:

```php
'Authorization' => 'Bearer ' . $this->config->get_license_key(),   // line 397
'Origin'        => $origin,                                        // untrailingslashit(home_url())
'Referer'       => trailingslashit($origin),
'User-Agent'    => self::USER_AGENT,
'X-Forwarded-Host' => $host,                                       // when parseable
```

plus, only on calls that reach an LLM or the embedder:

```php
'X-LLM-API-Key-Encrypted'       => $config->get_llm_api_key_encrypted(),
'X-Embedding-API-Key-Encrypted' => $config->get_embedding_api_key_encrypted(),  // only when set
'X-Embedding-Provider'          => $config->get_embedding_provider(),
'X-Embedding-Model'             => $config->get_embedding_model(),
```

The `Origin` / `Referer` / `X-Forwarded-Host` trio is not decoration. Its
comment says it plainly: this is a server-to-server call, nothing sets them for
us, and omitting them 403s every request. See trap 6.2.

Delete is one call (`class-api-client.php:154`):

```php
public function delete_item(string $entity_id, string $content_type = 'product') {
    return $this->post('/api/wordpress/productqa/sync/delete', [
        'items' => [['entity_id' => $entity_id, 'content_type' => $content_type]],
    ], false);
}
```

`false` = do not attach the provider-key headers. A delete reaches no model, so
sending a key to it widens its exposure for nothing.

The backend side of that call,
`backend/app/wordpress/productqa/routers/sync.py:418`, is the reference
implementation for what we need on the semantic-search namespace: it resolves
the licence from the request, iterates items, swallows per-item failures
(deleting something that was never indexed must not look like a failure), and
invalidates the results cache once at the end.

## 4. The three webhook-registration files

These are the files whose reason to exist is webhook registration.

### 4.1 `semantic-search-woo/includes/class-webhook-manager.php` — DELETE ENTIRELY

340 lines, all of it obsolete:

* `register()` / `create_webhook()` / `delete_existing()` / `delete_webhook()` /
  `webhook_exists()` / `delete_by_name_pattern()` — creating and reaping
  WooCommerce webhooks. Replaced by `SSW_Sync::register_hooks()`, which needs no
  registration step at all: WordPress hooks are wired on every request.
* `check_status()` — "are all three webhooks alive". Nothing to check once
  there are no webhooks.
* `get_client_id()` — resolves `client_id` from the licence key via
  `GET /api/status`, solely so it can be pasted into the delivery URL. Under the
  push method the server resolves identity from the presented key, so the plugin
  never needs to know its own `client_id`.
* `generate_secret()` and `send_secret_to_api()` — the HMAC secret and the push
  to `/api/register-webhook-secret`. Obsolete: the Bearer key authenticates the
  caller, so there is no second shared secret.
* `wc_request()` and the `ssw_wc_key` / `ssw_wc_secret` pair it needs. **The
  merchant no longer has to create WooCommerce REST API credentials at all.**
  That is the single biggest win in this change — it removes the setup step that
  most often stalls onboarding, and it removes a stored credential that granted
  our plugin write access to the whole WooCommerce REST API.

Nothing replaces this file. It is deleted, and `SSW_Sync` absorbs the two events
it was really there to deliver (delete and unpublish).

## 6. Traps

### 6.1 The unpublish path has never worked, and two other delete call sites are broken the same way

`qdrant_service.delete_product` is `(client_id, domain, product_id)`. It was
being called with two arguments in three places:

* `backend/app/routers/webhooks.py` `process_upsert` — **fixed in this change.**
  Every unpublished product raised `TypeError`, the endpoint's blanket
  `except Exception` turned it into a 500, and the point was never removed. A
  product pulled out of `publish` kept answering shoppers from the index
  indefinitely. Nothing else covered it, because `SSW_Sync::sync_single()`
  deliberately stands down for a non-published product on the stated grounds
  that removal is that webhook's job.
* `backend/app/routers/ingest.py:131` — still broken. This is why you must not
  repoint the plugin at `POST /api/ingest/delete`.
* `backend/app/routers/magento.py:829` — still broken. Someone else's file;
  flagged here because it is the same defect and will bite the Magento delete
  path the same way.

Do not treat "the webhook handles removal" as a description of anything that
was actually happening in the field.

### 6.2 Moving to push moves this traffic under `DomainAuthorizer`

`webhooks.py` never calls it. `POST /api/sync/batch` does
(`routers/sync.py:146`), and so will the new delete endpoint.

`DomainAuthorizer._validate_request_headers`
(`backend/app/services/domain_auth_service.py:112`, gated at line 79) requires
that **at least one** of `Origin`, `Referer`, `X-Forwarded-Host` resolve to the
licensed domain, and 403s when none does. It early-returns for private/loopback
client IPs, and the whole layer can be killed with
`AICHATBOT_DOMAIN_ENFORCEMENT=0`.

`SSW_Sync::send_batch()` sends none of those headers today
(`class-sync.php:538-542` — `Content-Type` only). That means full sync from this
plugin passes only because the deployments it has been exercised against are
local or have enforcement off. Send the trio, the way
`AIPQA_API_Client::build_headers()` does, before this reaches a production
store. This is the single most likely way the cutover fails in the field, and it
will present as "sync suddenly 403s" with no obvious connection to the webhook
change.

### 6.3 Delivery-URL provider keys were a snapshot; hook-time keys are not

Under webhooks, a merchant who added an embedding key had to re-register to pick
it up, because the key was frozen into the delivery URL
(`class-webhook-manager.php:74-85`). Under push, `SSW_API_Client` reads
`ssw_embedding_api_key` at request time, so a newly added key takes effect on
the next save with no re-registration. That is strictly better — just do not
carry the "re-register to pick up your new key" copy across into the new UI.

### 6.4 Webhooks already registered in merchants' stores outlive the plugin change

They live in the merchant's WooCommerce install, not in ours. Deleting
`ssw_deactivate()`'s reap without a replacement leaves three orphaned webhooks
per store POSTing at a route that no longer exists, forever. See section 8.

## 7. Residual issue: the KEK is still `sha256(license_key)`

**This change does not fix that, and it is worth being explicit that it does
not.**

After the cutover the server never reads a licence key back out of the database
— that is the whole point — but the derivation is unchanged. The licence key is
still both:

* the **authentication credential**, presented on every request, which you want
  to be able to rotate freely and must rotate immediately on compromise; and
* the **key-encryption key** for the merchant's LLM and embedding API keys,
  which you want never to change, because changing it orphans every blob wrapped
  under the old one.

Those two lifecycles are in direct opposition. Rotating a licence key today
invalidates every wrapped provider key on that store, and the merchant has to
paste both keys in again.

### What already mitigates it, and exactly where the mitigation ends

Both plugins re-wrap during the save that changes the licence —
`SSW_Admin::store_provider_key()` (`admin/class-admin.php:551-592`), ported from
`AIPQA_Admin`. It unwraps with the OLD licence still in `wp_options` and re-wraps
under the new one, which is only possible inside that one request.

It covers the common path: operator reissues, merchant pastes the new key into
Settings, keys carry over. It does **not** cover:

* two licence changes with no save in between — the blob is already orphaned by
  the first;
* a restored database backup, or a plugin reinstall, where the old licence key
  is gone but the wrapped blob survives;
* a fresh install configured with the new licence — the blob was never readable
  there;
* any rotation performed anywhere other than that settings save.

In all of those the failure is silent in the worst way: `resolve_embedding_key`
treats a blob that will not decrypt as absent
(`backend/app/services/embedding_key_service.py:73-80` — logs a warning and
continues), so the backend falls back to the server's own key and **the
merchant's usage lands on Czargroup's billing account**. That is exactly the
failure commit `4fa0698` describes. The plugin now warns per-field on save and
on render, which is the best that can be done from inside a design where the
credential and the KEK are the same string.

### What a site-scoped KEK would change

Mint a random 32-byte secret per site when the site row is created, store it on
`sites`, and hand it to the plugin once — at onboarding, or alongside licence
issue. Wrap provider keys under **that**, never under the licence key.

* Licence rotation becomes a pure authentication event: revoke, reissue, evict
  the cached `key_hash`. Wrapped provider keys are untouched and the merchant
  re-enters nothing. Every bullet in the uncovered list above disappears.
* Site scope, not subscription scope, is the right level: every module on one
  store shares one Qdrant collection and one set of provider keys, so a
  per-module KEK would mean the same key wrapped five times.
* The cost is real and should not be glossed: today, after the migration, the
  server holds no KEK at all — it only ever sees one the caller hands it, which
  is exactly the property being sold ("a database dump is not a handover of
  every customer's credential"). A site-scoped KEK puts server-held key material
  back in the database. To keep the property, the site secret must itself be
  wrapped under a master key held outside the database (env var or KMS). The
  design question is master-key custody, not whether the scoping is right.
* The one-time migration cannot be done server-side, because after the schema
  change the server cannot read any existing blob. It has to be done in each
  plugin, in one save that still has both secrets — the same case-2 machinery
  `store_provider_key()` already implements. Merchants who miss that window
  re-enter their keys once, which is the status quo cost anyway.

Recommendation: do it, but as its own change, after this one. Bundling a
credential-scheme change into a transport change makes both untestable.

## 8. Cutover order

1. **Backend first, additively.** Bearer on `/api/sync/batch`, new
   `POST /api/sync/delete`. Nothing is removed; old plugins keep working.
2. **Ship the plugin change.** Delete hooks, unpublish handling, Bearer + domain
   headers, webhook UI removed.
3. **Reap in-field webhooks.** Keep `ssw_deactivate()`'s
   `SSW_Webhook_Manager::delete_existing()` for **one** release, or move the reap
   into a one-shot upgrade routine that runs on version bump, so stores that
   already have three registered webhooks stop POSTing at a dead route. Only then
   delete `class-webhook-manager.php`.
4. **Remove the backend path.** `routers/webhooks.py`,
   `routers/webhook_secret.py`, their two `include_router` lines, and
   `license_service.get_client_license()`.
5. **Then the schema migration.** Note the interaction: `migrate_v2_schema`'s
   `move_webhook_secrets` phase copies `clients.webhook_secret` onto `sites` and
   then drops the client column, and the adversarial review flagged it as a data
   loss for clients that hold a secret but own no site row. If steps 1-4 land
   first, that phase and `sites.webhook_secret` are moving a value nothing reads.
   Confirm with the migration owner rather than assuming — but do not drop the
   column before the plugin cutover has actually shipped to stores.

Steps 1-2 are independent of the schema migration and can ship now. Step 4 is
the one that must precede the migration, because after it the schema change no
longer breaks anything that is still running.
